# OTLP Endpoints: 443 vs 4317 vs 4318

When you export OpenTelemetry traces directly to a backend like New Relic, you eventually
hit a confusing decision: should the endpoint be `:4317`, `:4318`, or no port at all?
People often assume these are interchangeable and that you can "just change the port."

You can't. The port is tied to the **protocol**, and the protocol is tied to the
**exporter class** you instantiate. This post explains the mapping, shows Java code for
each option, and recommends what to use behind a corporate firewall.

## TL;DR

- **4317 and 4318 are NOT interchangeable by changing the port alone.**
- `OtlpGrpcSpanExporter` → **gRPC** → port **4317** → **no path**.
- `OtlpHttpSpanExporter` → **HTTP/protobuf** → port **4318** → path **`/v1/traces`** required.
- Behind an enterprise firewall, prefer **HTTP on 443** (omit the custom port).

## Port / protocol reference

| Port | Protocol | Transport | Java exporter class | Endpoint shape |
|------|----------|-----------|---------------------|----------------|
| 4317 | OTLP/gRPC | HTTP/2 | `OtlpGrpcSpanExporter` | `https://host:4317` (no path) |
| 4318 | OTLP/HTTP | HTTP/1.1 | `OtlpHttpSpanExporter` | `https://host:4318/v1/traces` (path required) |
| 443  | either | gRPC or HTTP over 443 | either | `https://host` (port omitted → 443) |

The `/v1/traces` path is part of the OTLP/HTTP spec — HTTP exporters build per-signal
URLs (`/v1/traces`, `/v1/metrics`, `/v1/logs`). gRPC does **not** use a path. Forgetting
the path when switching to HTTP is the single most common "I just changed the port and
now it's broken" mistake.

> Most managed backends accept all protocols on the same host. New Relic, for example,
> exposes `https://otlp.nr-data.net` and accepts gRPC, http/protobuf, and http/json on
> ports 443, 4317, and 4318. Use the US host `otlp.nr-data.net` or the EU host
> `otlp.eu01.nr-data.net` depending on your account region.

## Which is more reliable behind an enterprise firewall

**HTTP on 443 wins.** Three reasons:

1. **gRPC needs HTTP/2 end-to-end.** Many corporate forward proxies, TLS-inspection
   appliances, and older firewalls don't support HTTP/2 or silently downgrade/break it.
   gRPC's long-lived streams also get killed by proxy idle timeouts, producing
   intermittent, hard-to-diagnose export failures.
2. **OTLP/HTTP is plain HTTP/1.1 request/response** — every proxy handles it cleanly.
3. **Non-standard ports (4317/4318) are frequently blocked** by egress rules that only
   permit 443.

Recommendation by situation:

| Situation | Endpoint | Exporter |
|-----------|----------|----------|
| Most reliable behind enterprise firewall | `https://host/v1/traces` (443) | `OtlpHttpSpanExporter` |
| Keep gRPC, minimize port issues | `https://host` (443, port omitted) | `OtlpGrpcSpanExporter` |
| Open network / local collector | `:4317` or `:4318` | either |

## Java code examples

These use the OpenTelemetry Java SDK. The gRPC exporter ships in
`io.opentelemetry:opentelemetry-exporter-otlp`; the HTTP exporter is in the same
umbrella artifact (it bundles both) or standalone in
`io.opentelemetry:opentelemetry-exporter-otlp-http-trace`.

### Option A — gRPC on 4317

```java
import io.opentelemetry.exporter.otlp.trace.OtlpGrpcSpanExporter;
import io.opentelemetry.sdk.trace.export.SpanExporter;

SpanExporter exporter = OtlpGrpcSpanExporter.builder()
        .setEndpoint("https://otlp.nr-data.net:4317")   // no path for gRPC
        .addHeader("api-key", apiKey)
        .build();
```

- Works fine on open networks.
- Brittle behind HTTP/2-unfriendly proxies.

### Option B — gRPC on 443 (port omitted)

Same exporter, just drop the port so it defaults to 443.

```java
import io.opentelemetry.exporter.otlp.trace.OtlpGrpcSpanExporter;
import io.opentelemetry.sdk.trace.export.SpanExporter;

SpanExporter exporter = OtlpGrpcSpanExporter.builder()
        .setEndpoint("https://otlp.nr-data.net")        // → 443, still gRPC
        .addHeader("api-key", apiKey)
        .build();
```

- Avoids the blocked-custom-port problem.
- Still carries gRPC/HTTP/2 fragility through proxies.

### Option C — HTTP on 4318

```java
import io.opentelemetry.exporter.otlp.http.trace.OtlpHttpSpanExporter;
import io.opentelemetry.sdk.trace.export.SpanExporter;

SpanExporter exporter = OtlpHttpSpanExporter.builder()
        .setEndpoint("https://otlp.nr-data.net:4318/v1/traces")  // path REQUIRED
        .addHeader("api-key", apiKey)
        .build();
```

- Plain HTTP/1.1 — proxy-friendly.
- Custom port may still be blocked by egress rules → prefer Option D.

### Option D — HTTP on 443, port omitted (recommended behind firewalls)

```java
import io.opentelemetry.exporter.otlp.http.trace.OtlpHttpSpanExporter;
import io.opentelemetry.sdk.trace.export.SpanExporter;

SpanExporter exporter = OtlpHttpSpanExporter.builder()
        .setEndpoint("https://otlp.nr-data.net/v1/traces")  // 443 + path, HTTP/1.1
        .addHeader("api-key", apiKey)
        .build();
```

- Standard port, standard HTTP, no HTTP/2 requirement.
- Most reliable through corporate proxies and TLS inspection.

### Wiring an exporter into a tracer provider

The exporter choice is independent of the rest of the SDK setup — any `SpanExporter`
plugs into a `BatchSpanProcessor` the same way:

```java
import io.opentelemetry.sdk.trace.SdkTracerProvider;
import io.opentelemetry.sdk.trace.export.BatchSpanProcessor;

SdkTracerProvider tracerProvider = SdkTracerProvider.builder()
        .addSpanProcessor(BatchSpanProcessor.builder(exporter).build())
        .build();
```

### Configuration-only alternative (no code)

If you'd rather not hard-code the exporter, the OTel SDK reads standard environment
variables. The autoconfigure module picks the exporter based on `OTEL_EXPORTER_OTLP_PROTOCOL`:

```bash
# HTTP on 443 — the firewall-friendly default
export OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
export OTEL_EXPORTER_OTLP_ENDPOINT=https://otlp.nr-data.net
export OTEL_EXPORTER_OTLP_HEADERS=api-key=YOUR_KEY

# gRPC equivalent
export OTEL_EXPORTER_OTLP_PROTOCOL=grpc
export OTEL_EXPORTER_OTLP_ENDPOINT=https://otlp.nr-data.net
```

With `OTEL_EXPORTER_OTLP_ENDPOINT` (the base URL), the HTTP exporter automatically
appends `/v1/traces`, `/v1/metrics`, etc. — so you give it the bare host and it builds
the per-signal paths for you.

## Gotchas

- **Path matters.** gRPC endpoints have **no** path; HTTP endpoints **require**
  `/v1/traces` (unless you use the bare-base-URL env var, which appends it for you).
- **Region.** Confirm the correct host for your backend region before changing defaults.
- **Dependency.** The HTTP exporter lives in `opentelemetry-exporter-otlp-http-trace`.
  The umbrella `opentelemetry-exporter-otlp` artifact includes both gRPC and HTTP.
- **Protocol mismatch is silent-ish.** Pointing a gRPC exporter at an HTTP port (or vice
  versa) typically fails with cryptic connection/parse errors rather than a clear
  "wrong protocol" message — check the port/exporter pairing first.
